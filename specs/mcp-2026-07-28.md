# MCP 2026-07-28 — migrating ScalaScript's MCP stack to the stateless revision

> Status: **complete** (2026-08-13) — every phase in §6 is landed or superseded by the
> sub-phases that replaced it. We serve BOTH revisions off one dispatcher: a request carrying
> `io.modelcontextprotocol/protocolVersion` in `params._meta` is modern, anything else is legacy
> and takes the path it always took. `SupportedProtocolVersions` is
> `2026-07-28`, `2025-03-26`, `2024-11-05`.
>
> What is deliberately NOT here, each with its reasoning written down rather than left implied:
> client-side Dynamic Client Registration, persisted client credentials and Client ID Metadata
> Documents (§9 — we implement the authorization SERVER side, so these have no subject);
> Sampling (§9.3 — never implemented; we provide the transport it rides on);
> and the managed state machine behind `save()` (§8.6, §8.9 — `ParkThenReplay` covers the case
> it was wanted for).
> Companion: [`specs/mcp.md`](mcp.md) — the original design (API shape, backend strategy).
> That document stays the source for *what our MCP API looks like to a `.ssc` user*;
> this one is the source for *which protocol revision we speak on the wire*.

Upstream: [MCP `2026-07-28` changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog).

## 1. Where we actually were (2026-08-09) — the starting point, kept

Read this as the survey that opened the migration, not as status; the status is at the top of
the file and §6 has the per-phase truth. Two things below have since changed and are worth
naming here so the section cannot be misread: the version string is now `2025-03-26` for the
legacy answer with `2026-07-28` alongside it (P1b), and every row of the surface table has been
moved or rewritten.

`McpProtocol.ProtocolVersion` said `2024-11-05`. The code says otherwise: we implement
tool/resource annotations, `title`, `outputSchema` + `structuredContent`, `resource_link`,
`audio` content, elicitation, completions, resource templates, pagination, cancellation and
progress. That is roughly the **`2025-06-18`** feature set. The version string has been stale
for two revisions — it under-reports, which is the harmless direction, but it means no client
can negotiate the features we do have.

Implementation surface, all of which eventually has to move:

| Path | Role |
|---|---|
| `mcp/common/.../mcp/McpProtocol.scala` | method names, envelope builders, version |
| `mcp/common/.../mcp/McpServerCore.scala` | transport-agnostic server + `dispatch` |
| `mcp/common/.../mcp/McpClientCore.scala`, `McpHttpClient.scala`, `McpWsClient.scala` | clients |
| `v1/runtime/std/mcp-plugin/.../McpIntrinsics.scala` | interpreter intrinsics |
| `v1/runtime/backend/jvm/.../JvmRuntimeMcp.scala` | JVM codegen runtime |
| `v1/runtime/backend/js/.../JsRuntimeMcp*.scala` | JS / browser runtime |
| `v2/runtime/providers/mcp-plugin/.../McpNativePlugin.scala` | native front |
| `v1/runtime/std/mcp/{server,client}.ssc` | the `.ssc` user API |
| `examples/mcp-*.{ssc,js}`, `tests/conformance/mcp-*.ssc` | examples + conformance |

**Two things we do not have to remove, because we never built them:** protocol-level sessions
(`Mcp-Session-Id`) and SSE stream resumability (`Last-Event-ID`, event ids). Verified by grep
over the whole repo on 2026-08-09 — zero hits. Those are the two hardest deletions in the
revision, and for us they are free.

## 2. What the revision changes

Nine major changes. Mapped onto our code:

| # | Change | Our exposure |
|---|---|---|
| 1 | Sessions + `Mcp-Session-Id` removed | **none** — never implemented |
| 2 | Stateless: `initialize`/`notifications/initialized` removed; version + capabilities + identity move to per-request `_meta` | `McpServerCore.dispatch`, `serve`, `handleHttpRequest`; 4 sites building `initializeResult` |
| 3 | `server/discover` — servers **MUST** implement | new |
| 4 | `subscriptions/listen` replaces GET-SSE + `resources/subscribe`/`unsubscribe` | `subscribeResource`, `unsubscribeResource`, subscriber plumbing |
| 5 | `ping`, `logging/setLevel`, `notifications/roots/list_changed` removed | all three implemented |
| 6 | Tasks → official extension `io.modelcontextprotocol/tasks` | not implemented — greenfield |
| 7 | MRTR replaces server-initiated requests | `srv.request(...)`, `listRoots()`, `elicitation/create` |
| 8 | `resultType` required on every result | every envelope builder |
| 9 | SSE resumability removed | **none** — never implemented |

Minor ones that touch us: `extensions` on capabilities; deterministic `tools/list` order;
`Mcp-Method`/`Mcp-Name` request headers + `x-mcp-header`; `CacheableResult` (`ttlMs` +
`cacheScope`) on five results; resource-not-found `-32002` → `-32602`; error-code allocation
policy (`-32020`…`-32099` reserved for the spec); JSON Schema 2020-12 loosening.

Deprecated (12-month window, still functional): Roots, Sampling, Logging; HTTP+SSE transport;
OAuth Dynamic Client Registration in favour of Client ID Metadata Documents.

## 3. Decision — dual-era, not a cutover

We implement **both eras on the same server**, and the spec explicitly sanctions this: the
versioning page names the configuration *"dual-era"* and gives it its own row in the
compatibility matrix (`Legacy client × Dual-era server → Works`).

A hard cutover was rejected: `2026-07-28` deletes `initialize`, so every existing client —
including every currently-shipping MCP host — would stop working the moment we flipped the
constant. The cost of dual-era is one branch in `dispatch`; the cost of a cutover is every
user.

**Era discriminator, per the spec:** *"A request carrying modern per-request `_meta` is served
statelessly according to this revision. An `initialize` request selects legacy semantics."*
Concretely — a request whose `params._meta` carries
`io.modelcontextprotocol/protocolVersion` is **modern**; anything else is **legacy**.
`server/discover` is answered in both eras, because it is also the stdio backward-compat probe.

Rejected alternatives, parked with their reasons:

- **Hard cutover to `2026-07-28` only.** Breaks every existing client. Revisit when the
  ecosystem has moved and legacy traffic is measurably zero.
- **A second server class (`McpModernServerCore`).** Duplicates the whole registry and every
  handler for one branch's worth of difference; guarantees the two drift.
- **Version-gate every envelope builder.** Would thread a version parameter through ~15
  builders. Instead the modern path *post-processes* the legacy envelope (§4.3) — one place,
  and it makes the legacy bytes provably unchanged.

## 4. P1 — the core stateless envelope

Scope: `McpProtocol.scala`, `McpServerCore.scala`, and one new test file. P1 deliberately
does **not** touch the four other `initializeResult` call sites — see §6.

### 4.1 Constants

```scala
val ProtocolVersion        = "2024-11-05"   // UNCHANGED in P1 — what `initialize` answers
val ModernProtocolVersion  = "2026-07-28"   // the stateless revision
val SupportedProtocolVersions = List("2026-07-28", "2025-06-18", "2025-03-26", "2024-11-05")
```

`ProtocolVersion` keeps both its name and its value in P1. It is read by three sites in
`McpIntrinsics.scala` and one in `McpNativePlugin.scala`, none of which are in this claim;
changing it here would silently change what those legacy servers advertise while leaving them
without the matching negotiation logic — the "second decision site, same front" trap. Bumping
it to the honest `2025-06-18` is slice 2, together with proper legacy negotiation at all four
sites. Recorded here so the omission is deliberate and findable.

New: `Method.ServerDiscover`, a `MetaKey` object for the six reserved `_meta` keys, and an
`ErrorCode` object for the three spec-allocated codes (`-32020` `HeaderMismatch`, `-32021`
`MissingRequiredClientCapability`, `-32022` `UnsupportedProtocolVersion`).

### 4.2 Per-request context

```scala
case class RequestContext(
  protocolVersion:    Option[String],
  clientInfo:         Option[ujson.Value],
  clientCapabilities: Option[ujson.Value],
  logLevel:           Option[String]
):
  def isModern: Boolean = protocolVersion.isDefined
```

`parseRequestMeta(params)` reads `params._meta` defensively — a malformed `_meta` yields an
all-`None` context, i.e. legacy, never an exception.

Validation on the modern path, in this order:

1. `protocolVersion` absent → legacy, no validation (dual-era leniency).
2. `protocolVersion` present but not in `SupportedProtocolVersions` → `-32022`, with
   `data = {supported: [...], requested: "..."}`.
3. `protocolVersion` present, `clientCapabilities` absent → `-32602`. The spec marks
   `clientCapabilities` **required** on every modern request.

### 4.3 Result post-processing — one site, not fifteen

The modern path takes the envelope the existing builders already produce and stamps it:

```scala
def stampComplete(result: ujson.Value, serverName: String, serverVersion: String): ujson.Value
```

— sets `resultType = "complete"` and merges
`_meta["io.modelcontextprotocol/serverInfo"] = {name, version}` without clobbering a `_meta`
the builder already wrote.

**This is what makes the change verifiable.** Legacy output must be byte-identical to
`origin/main`, and the gate asserts exactly that (§5) — so a bug in the modern path cannot
hide behind "well, the old tests still pass".

### 4.4 `server/discover`

Answered in both eras, no params required:

```json
{ "resultType": "complete",
  "supportedVersions": ["2026-07-28", "2025-06-18", "2025-03-26", "2024-11-05"],
  "capabilities": { "tools": {…}, "resources": {…}, "prompts": {…},
                    "logging": {}, "completions": {} },
  "_meta": { "io.modelcontextprotocol/serverInfo": { "name": …, "version": … } } }
```

`instructions` is optional and omitted (we have no server-level instructions field yet);
`ttlMs`/`cacheScope` land in P2 with the rest of `CacheableResult`.

## 4.5 Where the tests live — and the module boundary this exposed

`mcp/common` is already version-independent: it imports nothing from `v1`, and `build.sbt`
already gives it `scalatestTest`. What was misfiled is its **tests** — measured 2026-08-09,
**44 of the 51** `Mcp*Test` / `OAuth*Test` files under
`v1/runtime/backend/interpreter-plugin-tests/` contain no `v1` import at all. They test
`mcp/common` from inside a v1 module purely because that module happened to have a test
harness first. Only 7 genuinely need v1 (the script and interpreter-integration suites).

P1's own test therefore goes to `mcp/common/src/test/scala/scalascript/mcp/` — a directory that
did not exist until now — rather than adding a 52nd file to the wrong place.

**The other 44 followed on 2026-08-09 (`mcp-module-extraction`).** Their only non-JDK imports
are `org.scalatest.*`, `scalascript.{mcp,oauth,oidc}.*` and `com.sun.net.httpserver` — so the
move needed no `build.sbt` change and no new dependency, exactly as the survey predicted.

Two checks were worth the minutes they cost:

- **Cross-references before moving.** Three files that stay named three that move
  (`AgentMcpRoundTripTest`→`McpEndToEndTest`, `OAuthClientScriptTest`→`OAuthClientSdkTest`,
  `OAuthGuardScriptTest`→`OAuthGuardTest`). All three turned out to be *comments*, not code —
  but a shared test helper hiding in one of them would have broken the v1 module's compile, and
  the check is what turned that from a hope into a fact.
- **Purity of the move.** `git diff -M --numstat` shows **44 renames, 0 insertions, 0
  deletions**. That is the proof that no test was silently edited or dropped in transit; "both
  suites are green" alone would not have shown it.

After: `mcpCommon/test` 462 green (was 15), the 7 genuinely-v1 files stay put and
`backendInterpreterPluginTests` compiles and runs 71 green.

## 5. Verification

The apparatus rule applies (`AGENTS.md` §"measurement apparatus must COMPARE"): each check has
to be able to fail. New `mcp/common/src/test/.../Mcp2026StatelessTest`:

1. **Legacy is byte-identical.** `dispatch` of `initialize`, `tools/list`, `tools/call`,
   `resources/list`, `prompts/list` with no `_meta` produces frames with **no** `resultType`
   and **no** `serverInfo` `_meta`. Frozen against the strings `origin/main` produces.
2. **Modern stamps.** The same requests with a valid modern `_meta` carry
   `resultType == "complete"` and `_meta["io.modelcontextprotocol/serverInfo"]`.
3. **`server/discover`** returns `supportedVersions` containing `2026-07-28`, with
   `resultType` and `serverInfo`, both with and without `_meta` on the request.
4. **Unsupported version** → error `-32022`, `data.supported` non-empty, `data.requested`
   echoing the input.
5. **Missing `clientCapabilities`** on a modern request → `-32602`.
6. **Negative control:** revert `stampComplete` to identity and check 2 and 3 fail.

Result, 2026-08-09: 15/15 green. The two frozen frames were written by hand from the builders
and matched byte for byte on the first run, which is the actual evidence that the legacy path
is untouched. Negative control run: with `stampComplete` neutered, exactly the four modern
cases fail and **all four legacy cases still pass** — so the legacy assertions do not
accidentally depend on the feature they are supposed to be blind to. Legacy suite at scale:
`backendInterpreterPluginTests/testOnly scalascript.Mcp* scalascript.AgentMcp*` — 187/187.

Gates: `scripts/smoke-ci`, `mcpCommon/test`, plus the legacy suite above (entirely legacy-path,
so any red there is a regression in the era we promised not to touch).

## 6. Phases after P1

Each is its own claim, its own spec section update, its own push.

- **`mcp-module-extraction` — make the library's independence structural** (Sergiy, 2026-08-09:
  *"вынести mcp в отдельный независимый от версии модуль и библиотеку"*). The code is already
  independent; the layout does not say so. Move the 44 v1-free test files into
  `mcp/common/src/test/`, move `v1/runtime/std/mcp/{server,client}.ssc` to a version-neutral
  home, and leave `v1/runtime/std/mcp-plugin` and `v2/runtime/providers/mcp-plugin` as what they
  actually are — thin per-front adapters onto one library. No `build.sbt` change for the test
  move. **Do this before P2**, or every remaining phase pays the relocation cost twice.
- **P1b — version honesty.** ✓ Landed 2026-08-09, with two corrections to what §4.1 predicted,
  both found by looking rather than by reasoning.

  **The "four `initialize` sites" are one server and four clients.** The three reads in
  `McpIntrinsics` and the one in `McpNativePlugin` populate the `protocolVersion` of an
  *outgoing* `initialize` request; the only place building an `initializeResult` is
  `McpProtocol`, via `McpServerCore.dispatch`. §4.1's stated reason for deferring the bump —
  "those servers would claim more than they can back" — was wrong in its details. The
  conclusion it led to (do not move a shared constant without reading every consumer) still
  held, for a different reason.

  **The honest version is `2025-03-26`, not `2025-06-18`.** Audited before advertising, which is
  the entire point of the phase. Present: tool annotations, audio content, completions,
  Streamable HTTP, OAuth, resource templates, progress `message`. **Absent, measured at zero
  occurrences:** the `MCP-Protocol-Version` HTTP header and the `context` field on
  `completion/complete` — both `2025-06-18` requirements. Advertising it would have swapped a
  four-revision UNDER-claim for an over-claim, the same defect pointing the other way.
  `2025-06-18` is therefore also removed from `SupportedProtocolVersions`, so neither the modern
  `-32022` path nor `server/discover` can offer it. P2 owns the header; both move together then.

  Delivered: `negotiateLegacyVersion`. `initialize` now honours the client's requested revision
  when we implement it and falls back to our best otherwise. Before this, `params.protocolVersion`
  was read by nobody and one hardcoded string came back, so a client asking for a supported
  revision was answered correctly only by coincidence. `LegacyProtocolVersions` is derived from
  the supported list by excluding the modern one **by construction**, so the handshake can never
  settle on `2026-07-28` — a revision in which the `initialize` the client just sent does not
  exist.
- **P2a — CacheableResult.** ✓ Landed 2026-08-09. **Six** operations, not five as §2 guessed:
  `server/discover` joins the four lists and `resources/read`. The hints ride the same single
  post-processing site as `resultType`, which falls out of the spec rather than being a
  convenience — hints belong only on `resultType: "complete"` results, so "where resultType is
  stamped" and "where hints are stamped" are the same place by construction, and the legacy path
  stays hint-free for the same reason it stays `resultType`-free.

  Two judgement calls, both resolved by using information we have instead of guessing:

  - **`cacheScope` is derived from whether a token validator is registered.** Auth on ⇒ every
    result belongs to some caller's authorization context and MUST NOT be shared across contexts
    ⇒ `private`. Auth off ⇒ one context, catalogue identical for all ⇒ `public`. Over-sharing
    leaks between callers, so the ambiguous case resolves to `private`.
  - **`resources/read` defaults to `ttlMs: 0`** — immediately stale — while lists default to
    60 s. A resource's content comes from a user handler we know nothing about; asserting a
    lifetime for it would claim a freshness the server cannot know, and the failure mode is a
    client serving stale data with no way to tell. The list TTL is defensible because our
    servers advertise `listChanged: true`, and the spec blesses TTL and notifications together:
    the notification invalidates immediately, the TTL only saves refetches in between.

  Negative control: make `cacheHintsFor` hint every method and exactly the two tests that assert
  the six-method boundary fail. Over-hinting is not harmlessly generous — a client told a result
  is cacheable will cache it, and `tools/call` is not cacheable at any TTL.

- **P2b — server-side header validation.** ✓ Landed 2026-08-09, minus `x-mcp-header`.
  `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` are checked against the body they claim to
  describe; any disagreement or absence is `-32020`. `Mcp-Name` is required only for the three
  methods that mirror a name (`tools/call`, `prompts/get`, `resources/read`) and is decoded
  through the `=?base64?…?=` sentinel before comparison. Header *names* compare
  case-insensitively per RFC 9110, values do not.

  The check exists because a load balancer may route on the header while this server executes
  the body: a request whose two copies disagree is one that two components would act on
  differently. That is why the spec makes it an error rather than a warning.

  **Modern requests only.** A legacy client never sent these headers and its revision never
  defined them; the spec explicitly permits treating a header-less request as `2025-03-26`,
  which is exactly our dual-era stance.

  **The gap this named is CLOSED (2026-08-10), and both reasons I gave for it were wrong.**
  I recorded that the plumbing could not be tested because "a route-level test needs a
  `PluginContext` double, of which there is none today". There is one — `OAuthHttpInstallerTest`
  has had the pattern all along, and it is three lines, since `NativeContext` declares only
  `out` and `err` abstract. And the double was never the obstacle anyway: `installHttpRoute`
  and `dispatchAuthorized` live in a **file-private** `object Mcp`, so they were *unreachable*
  from a test rather than merely undriven. Widened to `private[mcp]`, which keeps them off the
  public intrinsic surface while letting the plugin's own tests drive them.

  `McpHttpRouteTest` now drives the real route. The negative control — strip the header
  forwarding from both call sites — also corrected which test does the work: the case I had
  labelled "the one the gap was about", a header/body MISMATCH, **stays green either way**,
  because a modern request with no headers is rejected for a missing required header with the
  same `-32020`. The discriminator is the POSITIVE case: matching headers must be *served*,
  and without the plumbing they cannot be seen. The test comments now say that.

- **P2c — `x-mcp-header`, server half.** ✓ Landed 2026-08-10. A `tools/call`'s `Mcp-Param-{Name}`
  headers are validated against the arguments at the annotated property paths; any disagreement
  is `-32020`. Modern requests only, same reason as the standard headers.

  The presence rules are asymmetric and the asymmetry is load-bearing: a value present in the
  body MUST carry its header, a value absent or `null` MUST NOT, and **both** violations are
  errors. A client that quietly omits a header while sending the value is non-conforming
  precisely because an intermediary routing on that header would then be routing on nothing.

  Constraint enforcement lives in `xMcpHeaderParams`, which returns `Left(reason)` for a schema
  that breaks the rules — and rejecting is the correct outcome, not a nuisance: the spec makes a
  conforming client drop such a tool from `tools/list` entirely, so a server emitting one has
  published a tool nobody may call. Better found here. `number` is excluded by name because a
  float has no single canonical string form, so header and body could never be compared without
  a rounding rule. The traversal follows `properties` chains only — under `items`, `oneOf` or
  `$ref` there is no fixed path to read a value from, which is why the spec forbids it and why
  an annotation there is simply not collected.

  Negative control: make the validator never report a disagreement and the four-combination
  test fails, while the positive cases and the constraint tests — which call `xMcpHeaderParams`
  directly — stay green, which is the right blast radius.

  **Client half deferred to P2d.** Emitting these headers is only meaningful once our client
  speaks the modern era at all.

- **P2d-1 — the client envelope.** ✓ Landed 2026-08-10. `clientMeta`, `withClientMeta`,
  `mirroredHeaders` and `mirroredParamHeaders` — the exact counterpart of the server-side
  validators, and deliberately built second so they could be graded against them.

  **The gate is a round trip through our own server**, not each side's opinion of itself:
  whatever the client builds is dispatched at a real `McpServerBuilder` and must come back
  without an error. Two halves of one rule cannot drift while that holds — the non-ASCII
  `Mcp-Name` case is the one that breaks the moment only one side knows about the sentinel.

  **The negative control found the gate too weak and it was rewritten.** The first version
  called `validateRequestHeaders` alone; dropping the REQUIRED `clientCapabilities` left it
  green, because that field is checked in `dispatch` rather than in the header validator. A
  round-trip gate exercising one of two checks is not a round trip. Now it dispatches, and
  the same control fails three cases instead of one.

  `withClientMeta` merges rather than replaces because `_meta` is a shared namespace: a
  caller may have set `progressToken` there, and replacing it would silently switch off an
  opt-in with nothing to report it.

- **P2d-2 — the era DECISION.** ✓ Landed 2026-08-10 (the decision; the wiring is P2d-3).
  `eraFromProbe` for stdio and `eraFromHttp` for Streamable HTTP, both pure and therefore
  testable without a network.

  **The subtle half is that a modern server may answer the probe with an ERROR and still be
  modern.** Unsupported version, missing capability, header mismatch — each refuses this
  particular request while proving the server speaks the revision. Reading every error as
  legacy would send the client to `initialize` against a server that has no such method,
  which is the failure the compatibility matrix calls Modern-client × Legacy-server. So the
  three spec-allocated codes are a recognition set, not just a list of things that went
  wrong.

  On HTTP the same asymmetry appears as status-versus-body: a modern server uses `400` for
  its own errors, so the status cannot distinguish *you asked wrongly* from *I have never
  heard of this*. Only a recognised modern error in the BODY identifies the era.

  Checked against our own server rather than against my reading of the spec: dispatch
  `server/discover` for real and feed the answer to the client's decision, and do the same
  with a genuine `-32022` refusal, which must also come back Modern.

- **P2d-3 — `connect()` on `McpClientCore`.** ✓ Landed 2026-08-11. Probes with
  `server/discover`, settles the era once and caches it, and completes the `initialize`
  handshake ONLY when the probe says legacy.

  **`initialize` is now sent after knowing the era rather than before.** That inversion is
  the whole fix: sending it first is exactly what makes a client fail against a modern-only
  server, since the revision has no such method. And a modern server refusing the probe
  still gets no `initialize`, because refusal is not the same as not speaking the revision.

  Idempotent by design: a settled era short-circuits, because re-probing a legacy server
  would send it a SECOND `initialize`, which the lifecycle it negotiated does not allow.

  **Tested against real peers, synchronously.** The client's `write` computes the reply on
  the calling thread and feeds it straight back, so the response is queued before `request`
  polls — no threads, no sleeps, nothing that can pass at the wrong moment. Yesterday's two
  green-by-accident cases in P4b-4 were both timing; this shape cannot have that fault. The
  modern peer is our own `dispatch`, so the probe is graded by the server it will actually
  meet, and the legacy peer answers `MethodNotFound` to `server/discover` as a real one does.

- **P2d-4a — `connect()` on the other two clients.** ✓ Landed 2026-08-12.

  **The HTTP probe cannot go through `request`, and that is the finding.** On any non-2xx
  `McpHttpClient.request` collapses the status and body into
  `Left(InternalError, "HTTP 400: …")`, discarding the JSON-RPC error code — and that code
  is the entire signal: a modern server answers `400` with `-32022` and is still modern.
  Probing through `request` would classify every modern refusal as legacy and then send
  `initialize` to a server that has no such method. So `connect` sends its own request and
  hands the raw status and body to `eraFromHttp`. The negative control is exactly that
  mistake: probe via `request` and the 400-with-a-modern-error case fails.

  Tested against a REAL endpoint rather than a stub, because the whole HTTP rule is about
  what the status and body are — a stub returning an already-parsed value would skip the
  part under test.

  `McpWsClient` takes the STDIO rule instead: a persistent bidirectional channel has no
  status code to inspect, so it probes with `server/discover` and reads the JSON-RPC answer.
  **That gap is CLOSED (2026-08-12), and not by building a harness.** Investigating it showed
  the gap was a symptom: `connect()` existed THREE times, once per client class, and the two
  request-based copies were identical apart from whitespace. The unreachable one was the copy
  that contained nothing of its own.

  Building a WebSocket server to reach it was the wrong fix — the JDK ships a WS client and no
  server, so that meant hand-rolling RFC 6455 in a test to exercise code that should not have
  been there. The right fix was to delete the duplication: `McpProtocol.negotiateEra` now holds
  the rule, parameterised by the one genuinely transport-specific part — how the era is
  DECIDED. Each client is left with a one-line supplier and no branching, so **there is no
  longer any untested logic in the WS client**; what remains is a delegation whose every part
  is covered.

  This was also the P1b trap forming again: one rule with three decision sites, where a spec
  change must be applied three times and the copy nobody can run is the one that rots. A test
  now asserts that no client carries its own copy, and re-introducing one makes it fail.

- **P2d-4b — the call sites, and a correction to `connect()` itself.** ✓ Landed 2026-08-12.
  All four unconditional `initialize` calls are gone: `McpIntrinsics` HTTP, WS and spawn,
  plus `McpNativePlugin`'s spawn path. **No call site sends `initialize` before knowing the
  era any more**, which is the line the compatibility matrix's *Legacy client × Modern
  server → Fails* row was about.

  **`connect()` was wrong as landed, and only the consumers showed it.** It returned an

## 8. P3 — MRTR, and the one decision that is not an agent's to make

### 8.1 What the revision does to us

`2026-07-28` removes server-initiated requests. A server that needs sampling, elicitation or
roots no longer *sends* a request and waits; it **returns** an `InputRequiredResult`
(`resultType: "input_required"`) carrying `inputRequests`, and the client **retries the original
request** with matching `inputResponses`. `McpServerBuilder.request(...)` and its pending-response
map stop being the mechanism on the modern path.

### 8.2 Why this is not an internal refactor

It reaches the `.ssc` surface. `srv.listRoots()` and `srv.elicit(message, schema)` are exposed
through `McpIntrinsics` today as **blocking calls inside a tool handler** — ask the client, wait,
continue with the answer. Under MRTR the server cannot wait. The handler must end, and run again
later.

So the question is not how to encode `InputRequiredResult`. It is: **what happens to a `.ssc`
tool handler that calls `srv.elicit(...)` halfway through its work?**

### 8.3 Three answers, with what each costs

**(a) Replay.** Keep the API exactly as it looks today. On the first pass `srv.elicit(...)`
throws an internal control-flow signal that dispatch converts into an `InputRequiredResult`; on
the retry the handler runs **again from the top** and `srv.elicit(...)` returns the answer out of
`inputResponses` instead of throwing.

*Cost, and it is the whole trade:* everything the handler did before the elicitation happens
**twice**. A handler that writes a row, then asks the user to confirm, writes two rows. That is a
correctness hazard we would be introducing into user code that is correct today.
`requestState` exists for exactly this and helps a handler that is written to expect replay —
it does nothing for one that is not.

**(b) Continuation capture.** Suspend the handler at the elicitation point and resume it on the
retry, so nothing re-runs. **This project already has the machinery** —
[`durable-continuation-save-run.md`](durable-continuation-save-run.md),
[`effect-vm-continuations.md`](effect-vm-continuations.md),
[`durable-capsule-envelope.md`](durable-capsule-envelope.md) — which is why this is a real
option here and would not be in most codebases. Cost: the capture has to work for a handler
running on the interpreter lane *and* the native lane, and MCP would become the first consumer
outside the effects work.

**(c) Change the API.** Make handlers explicitly two-phase. Honest about the protocol, and it
breaks every existing `.ssc` server that elicits.

### 8.4 What I recommend, and what I am not deciding

**(a) for the modern path, with the legacy path keeping today's blocking behaviour unchanged** —
consistent with everything else in this migration, where the legacy era is served byte-identically
and the new one is added beside it. A `.ssc` server that never sees a modern client is unaffected.

I am not choosing it unilaterally, because §7 of this document says a phase that forces a
user-visible change belongs in review before it lands, and (a) does force one: the same handler
source becomes replay-sensitive the day a modern client connects to it. That is the kind of
change a user finds out about through a duplicated database row, not a compile error.

**Specifically worth a decision:** whether the replay hazard is acceptable given the project
already owns continuation machinery that could remove it. (b) is more work and more risk, but it
is the answer that does not put a footgun in `.ssc` handlers that are correct today.

### 8.5 What does NOT depend on that decision

These can land while the above is open, and each is independently verifiable:

- `InputRequiredResult` encoding + `resultType: "input_required"` on the wire, and the rule that
  such a result is **not cacheable** (§4 P2a's hints must not be stamped on it).
- `inputResponses` / `requestState` parsing on the way in.
- The MRTR results being excluded from the cacheable set — a retry carrying `inputResponses`
  depends on inputs outside the cache key, which the caching page states explicitly.
- Removing `ping`, `logging/setLevel` and `notifications/roots/list_changed` from the **modern**
  dispatch only, leaving the legacy path untouched.

### 8.5b DECIDED (Sergiy, 2026-08-10) — replay, and the managed machine stays parked

**The handler remains an ordinary unsavable closure and is RE-RUN on the retry.** Sergiy:
*"сначала делаем более простой вариант с несохраняемым замыканием и ретраями при необходимости,
а более сложный вариант с управляемым автоматом оставим на потом если потребуется."*

Read as path 2 of §8.6 (replay), not path 1 (parked thread) — the two are distinguished by
exactly one thing: **whether the handler runs again.** Under replay it does; under the parked
thread it never does. Recorded this way so a misreading is visible rather than buried.

**What it buys.** The server stays stateless: no instance affinity, no parked threads, no TTL on
abandoned subscriptions, multi-instance deployment for free. This is the shape MRTR was designed
for — *"without requiring a shared storage layer across server instances or requiring stateful
load balancing."*

**What it costs, and it is one thing.** Everything the handler did before `elicit` happens
**twice**. Write a row, ask for confirmation, write a second row. The failure is silent: not a
compile error, not an exception — a duplicated effect noticed later and somewhere else.

**So P3b's scope is larger than "return an InputRequiredResult".** It carries three obligations
that follow from the decision rather than from the protocol:

1. **`requestState` must carry what has already been done**, or an author cannot write an
   idempotent handler even when they want to. That is what the field is for.
2. **The contract belongs in the `.ssc` API docs, not only here.** `srv.elicit` acquires a
   precondition: *the code before this call must be idempotent.* A protocol spec is not where a
   `.ssc` author will look for it.
3. **Modern path only.** A legacy client keeps the blocking call and no re-run, so existing
   servers do not change behaviour — the same dual-era rule as everywhere else in this migration.

The managed machine (§8.6 path 3) stays recorded as the option that removes the cost, for the day
requiring idempotence from authors turns out to be too much to ask.

### 8.8 P3b as built (2026-08-12) — replay, and where it is enforced

`elicit` forks on the era. Legacy is byte for byte what it was: a server-initiated request that
blocks. Modern consults the answers the client echoed back — and if this question is not among
them, throws `InputRequiredSignal`, abandoning the handler so the dispatcher can answer
`InputRequiredResult`. The retry re-runs the handler from the top, which is the decision in
§8.5b and not an implementation detail: it is the one thing that distinguishes replay from a
parked thread, so the test that asserts it counts the handler's entries.

**Where the enforcement lives, and why it is split.** The decision — what the signal MEANS —
sits in `withRequestTracking`, the single wrapper all three MRTR-capable methods already went
through. But each of `callTool`, `readResource` and `getPrompt` wraps its handler in
`catch case e: Throwable`, which would have reported the signal as `isError` before the wrapper
ever saw it. So each carries one line that declines to swallow it and nothing more. Three
mechanical edits, one decision.

The tidier alternative was considered and rejected: make the signal a `ControlThrowable` and
change those three to `NonFatal`, so future paths would be right by construction. That also
changes what happens to `InterruptedException` in an ordinary handler — today it becomes an
`isError` result, and under `NonFatal` it would escape into the transport loop. A silent
behaviour change on the legacy era is not worth the tidiness.

**Keys.** Questions are matched to answers by a per-invocation counter, `elicit-1`, `elicit-2`.
Ordering is what makes this work and is also the whole of its precondition. An author who cannot
promise a stable sequence passes an explicit `key` instead.

**Obligation 1 is met, not deferred.** `requestState` round-trips, and `srv.requestState` /
`srv.setRequestState` let the handler read what it recorded and record for the next pass — what
the handler wrote wins, and absent that the client's value is echoed, so a stateless handler
still round-trips it. Exposed to `.ssc` as `srv.requestState()` / `srv.setRequestState(s)`, with
the untrusted-input warning at the intrinsic: the value travels to the client and back untouched.

**Obligation 2 is met where it will be read.** The precondition is on the `elicit` intrinsic in
`McpIntrinsics.scala`, in the comment a `.ssc` author meets, and it says the thing plainly: the
code before an `elicit` runs again, once per question; write a row and ask for confirmation and
you have written two rows.

**What is proven and what is argued.** Proven by test at two layers: `mcp/common` against
`handleHttpRequest`, and `McpHttpRouteTest` through the plugin's HTTP route, which is the entry
point a `.ssc` server actually reaches. Each has its own negative control and they fail for
different reasons — neutering the rethrow kills the first-pass case while the retry case still
passes, since on a retry no signal is thrown at all. **Since CLOSED — see §11.** At the time this was written the interpreter frame between a `.ssc`
closure and the intrinsic was proven by READING: `invoke` installs no catch-all, and the signal is
an ordinary `RuntimeException` on a path that already propagates `PluginError.raise`. That was an
argument, not a measurement, and was recorded as one; §11 replaces it with a measurement.

### 8.9 P3c (2026-08-12) — a parked virtual thread becomes the DEFAULT

Sergiy, while P3b was in flight: *"Предлагаю сделать по умолчанию припаркованный виртуальный
поток."* Then, on whether replay should catch the miss: *"Риплей если чтото гдето не получилось
и попало мимо не на тот хост или процесс."*

**The argument that decided it is about the SHAPE of the failure, not about convenience.**
Replay's cost is silent: everything before an `elicit` happens again, and a duplicated effect is
noticed later and somewhere else. A park's cost is loud: the retry cannot find the thread and the
client is told so. Between a default that fails quietly and one that fails audibly, the audible
one is the default, and Loom is what makes it affordable — a parked handler costs kilobytes of
heap rather than a platform thread.

**Three modes, and why the tempting one is not the default.** `Park` asks nothing of the author.
`Replay` is for multi-instance deployments and carries the idempotent-prefix precondition.
`ParkThenReplay` is Sergiy's proposal taken literally — park, and re-run when the park is missing
— and it is **opt-in**, because the fallback IS a replay: it carries `Replay`'s precondition and
breaks it rarely and unpredictably, which is the worst way for a duplicated effect to arrive. A
handler written under "you don't need idempotence, we park" would be wrong exactly in the rare
case. It is offered because for a single-process `.ssc` server the fallback almost never fires,
so opting in costs nothing where it is safe and protects the case where it is not.

Worth stating plainly: the loud failure is not free either. The first pass already performed its
pre-`elicit` effects on the instance that lost the park, so restarting the operation repeats them
too. The difference is that a loud failure makes that repetition someone's DECISION, where the
silent one just performs it.

**Why this needed no change to any transport.** The first estimate here was wrong and is worth
recording as such. Both transports serialize request handling today — stdio's `serve()` is a
single `while running do` loop, and the production HTTP backend uses a `newSingleThreadExecutor`
(`JdkServerBackend.scala:66`) — so it looked as though parking required making request handling
concurrent, a cross-cutting change to shipped v1 infrastructure. It does not. What parking needs
is only that the handler run on a DIFFERENT thread from the reader: the reader waits exactly as
long as it does today while the handler computes, and stops waiting the moment the handler asks a
question. The reader returns the `InputRequiredResult` and goes back to reading; the virtual
thread stays parked on its own. Everything lives inside `withRequestTracking`.

This is the same lesson the file already carried for `subscriptions/listen` — *"we MUST NOT
block: the loop has to keep reading, or the client could never send the cancellation"* — which is
why the deadlock was worth checking for before agreeing to the design rather than after.

**The token rides in `requestState`, which the author also owns.** The spec makes `requestState`
the only field a client must echo back, so the park token has nowhere else to live. The server
therefore owns an envelope, `{"park": …, "app": …}`, and `srv.requestState()` returns only the
author's slice. A value that does not parse as the envelope is treated as author state with no
token, which is what a `Replay`-mode server produced before parking existed. The token is
server-generated and validated on the way back, because that field is attacker-controlled.

**Bounded, because a parked thread is a resource a client can ask for.** A TTL (default five
minutes) expires abandoned parks, swept lazily when the next one is created rather than by a
reaper thread that every parkless server would also pay for. A ceiling (default 256) refuses a
NEW call rather than dropping an existing park — losing the caller whose work is already half
done is the worse trade. `notifications/cancelled` drops the park immediately instead of leaving
it to time out.

**Evidence.** `mcpCommon` 125 cases in this suite, and three negative controls, each precise:
forcing `parkingServer` to `Replay` fails exactly the five cases that are about parking and
leaves the three that build their own server alone; bypassing the loud-failure branch fails
exactly the two cases that depend on it; making the cancellation predicate `false` fails exactly
the cancellation case. The load-bearing assertion is a single number — the handler's entry count
reads 1 where P3b's reads 2 — because that number, and nothing else, is the difference between
the two modes.

### 8.6 Correction (2026-08-10) — continuation capture is not available, and not for want of building

§8.3 offered "continuation capture" as option (b) and said the machinery already exists here.
**That was wrong, and the error was mine twice over.** Reading
[`durable-continuation-save-run.md`](durable-continuation-save-run.md) and
[`control-interoperability.md`](control-interoperability.md) properly:

1. **`save()` succeeds only for `Savable`** — `Continuation.savable(state, machine, codec)`, a
   *managed* state machine with an explicit `DurableValue[S]`. A `.ssc` tool handler is the
   `Runtime` shape: *"an opaque host closure … has no reified frame; it is genuinely unsavable in
   the reference model."*
2. **That is a deliberate boundary, not a gap.** `control-interoperability.md` §FrameGate:
   *"Exact artifact pinning does not rescue a raw foreign object, live resource, native closure,
   or stack frame. `save` succeeds only for `Savable`."*
3. **The named follow-on slice does not close it.** `saved-continuation-format` (byte codec,
   §9.1 canonical encoding, depends on `coreir-codec-h4-h5`) makes *savable* continuations
   serialisable. It does not make a host stack frame savable, and nothing on that list does —
   because nothing is supposed to.

So "finish the continuation machinery, then come back" cannot reach P3b by itself. The three
paths that actually exist:

- **Parked thread + `requestState`.** Keep the handler blocked exactly as it is today and re-key
  the existing pending-response map from JSON-RPC id to `requestState`, so the retry wakes the
  same parked thread. No replay, no serialisation, no new machinery, and the `.ssc` API does not
  change. Cost: a thread per in-flight elicitation, a TTL and a cap so abandoned retries do not
  leak them, and **instance affinity** — the retry must reach the same process. MRTR was designed
  to avoid requiring that, so this is a single-process answer.
- **Replay.** Stateless and multi-instance safe; side effects before the elicitation happen twice.
- **Managed handlers.** Make an eliciting `.ssc` handler a `Savable` machine with a codec for its
  state. This is the architecturally honest answer and the only one that yields genuinely
  stateless MRTR — but it needs BOTH a user-facing API change AND `saved-continuation-format`,
  which is unbuilt and has its own dependency. It is a programme, not a phase of this migration.

**What this costs to get wrong is why it is written down rather than decided:** the first framing
sent the decision toward machinery that was never going to arrive, and the second would have
spent a slice in another module before discovering the same wall.

## 9. P5b — deprecations, and three items that turned out not to exist

P5b came off the changelog as five items. Three of them have no code here to change, and that
is the finding rather than a gap to be filled with speculative code:

| Changelog item | Verdict |
|---|---|
| `application_type` on Dynamic Client Registration | **non-item** — we have no client-side DCR |
| credentials keyed by issuer | **non-item** — we persist no client credentials |
| Client ID Metadata Documents | **non-item** — CIMD is an *alternative to* DCR, which we do not perform |
| our AS still serves `/register` (RFC 7591) | **keep** — the revision explicitly retains DCR for servers without CIMD |
| deprecate Roots and Logging | **real** — both are implemented |
| deprecate Sampling | **partly a non-item** — we implement no Sampling; see 9.3 |

The evidence for the first three is one grep and one read: `def register|application_type|
registration_endpoint` matches nothing in `oauth/OAuthClient.scala`, and `ClientStore` — the
thing that looked like stored credentials — is declared in `AuthServer.scala` as the
*authorization server's* registry of registered clients. We implement the server side of
registration and not the client side, so the client-side requirements have no subject.

This is the same treatment the GET → 405 item got in §2, and for the same reason: an item taken
from a changelog without reading our own routes is a claim about someone else's codebase.

### 9.1 Why the notices are prose and not `@deprecated`

The obvious mechanism is the Scala annotation. It is the wrong one here. This build runs
`-Werror`, so a deprecation warning is a compile error — and we call these methods ourselves, on
the legacy path we are contractually obliged to keep serving. `@deprecated` would either break
the build or have to be silenced at every internal call site, and a warning silenced everywhere
communicates nothing. The notice therefore lives at each definition, saying what to reach for
instead: tool parameters or resource URIs instead of Roots, direct provider integration instead
of Sampling, stderr or OpenTelemetry instead of Logging.

### 9.3 Sampling is not ours to deprecate, and how I nearly said otherwise

There is no Sampling in this codebase. No `Method.Sampling*` constant exists; every occurrence of
`sampling/createMessage` is a COMMENT citing it as an example. Sampling is a client-side feature —
the server asks, the client calls the model — and what we implement is the transport it rides on:
the bidirectional server-initiated request (`nextRequestId` / `serverPending`). That mechanism is
what 2026-07-28 replaces, with MRTR, so the notice belongs there and not on a feature we do not
have.

The first version of the table above said all three deprecated features were implemented. That
came from `grep -rl sampling/createMessage` returning four files — and those were four files
MENTIONING the string in prose. A census answers only the question asked, and the question
"which files contain this text" is not the question "do we implement this". The row is corrected
rather than quietly deleted, because the corrected row is the same shape as the three non-items
above it, and that shape is the actual finding of P5b: most of a changelog is about someone
else's codebase until you check.

### 9.2 The defect this uncovered — a removed notification nobody refused

Checking one of those notices against the code found a real gap. The notice said
`notifications/roots/list_changed` is removed in the modern era; `RemovedInModern` did not
contain it, and both notification paths — stdio and HTTP — called `onRootsListChanged()`
regardless of era. A modern client sent a method its own revision deleted, and we acted on it.

Adding the method to `RemovedInModern` would have looked like the fix and changed nothing:
that set is read only by `dispatch`, which is the **request** path. A notification never reaches
it. The two are now separate sets, `RemovedInModern` and `RemovedNotificationsInModern`, kept
apart deliberately and documented as such — because they are enforced in different places by
necessity. A removed request is refused with `MethodNotFound`; a removed notification has no
response at all, so the only refusal available is to not act on it.

Enforcement is one private helper called from both notification paths, not two conditionals: a
rule applied on one of two paths is not applied. A notification with no `_meta.protocolVersion`
is legacy and is delivered exactly as before — that is also the safe direction to be wrong in,
since the alternative silently drops a legacy client's notification.

**A note on how the tests read.** The first run after the fix failed exactly one case, the
modern one, and seven reruns were green. That looked like a flaky test and was not: `sbtc` had
served a stale artifact, the caveat already recorded under *Build speed & hygiene*. The
distinction mattered — a "flake" gets rerun until green, and this needed the run repeated
against a rebuilt artifact. The negative control was then obtained by accident and is worth
more than the reruns: with the guard absent, exactly that one case fails.


## 10. P5c — the Tasks extension

Read from the source rather than from the changelog row, because a one-line row naming an
extension is not a specification and building from it would have been inventing a protocol and
calling it MCP. The authority used here is
[the extension site](https://tasks.extensions.modelcontextprotocol.io/) and
[SEP-2663](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/seps/2663-tasks-extension.md),
against the [core 2026-07-28 basic spec](https://modelcontextprotocol.io/specification/2026-07-28/basic/index).

**What it is.** A server may answer `tools/call` with a task handle instead of a result:
`resultType: "task"` plus a `taskId`, and the client polls `tasks/get` until the status is
terminal. Five statuses — `working` and `input_required` are non-terminal, `completed`, `failed`
and `cancelled` are terminal. `tasks/update` supplies mid-flight input; `tasks/cancel` asks,
cooperatively. There is **no `tasks/list`**, deliberately: a task id is a capability, and an
enumeration endpoint would hand out every one of them.

**The server is the sole decider.** SEP-2663 is explicit — *"clients do not signal task
preference on the request itself"* — and, unlike the 2025-11-25 experiment, `tools/list` does not
advertise per-tool task support. So there is nothing to parse on the way in and no per-tool flag
to register; the decision is made inside the handler, which is what P5c-2's `srv.asTask()` will
be.

### 10.1 Two pages of one specification disagreed, and the core one wins

The extension page gives `-32003` for a missing tasks capability. That value sits in the
`-32000`..`-32019` sub-range which the core spec calls **legacy** and says new implementations
**MUST NOT** allocate in and **SHOULD NOT** use at all; the same core page lists
`MissingRequiredClientCapability` as **`-32021`**. We emit `-32021`, and the reason is recorded
because the temptation ran the other way: having read `-32003` first, I went to "correct" our
already-landed `-32021` and found the landed value was right. Where two pages disagree, the one
that defines the allocation policy is the one to believe.

Two other conformance items were checked against the core spec in the same pass and needed
nothing: we never emit `-32002` (a test asserts it), and `clientCapabilities` is already enforced
as a required per-request field answered with `-32602`. Recorded because "checked and already
correct" is a result, and the next person should not re-derive it.

### 10.2 Why the hard part is already built

The extension's `input_required` state is MRTR's mechanism wearing a different hat, down to the
shape of `inputRequests` — `{key: {method, params}}` in both. And a task is exactly what P3c
already produces: a handler suspended on a virtual thread behind an unguessable handle, with a
TTL and a cancellation path. The correspondence is close enough to name:

| Tasks extension | P3c, already shipped |
|---|---|
| `taskId` | the park token |
| `ttlMs` | `parkTtlMs` |
| `input_required` + `inputRequests` | `ParkOutcome.NeedsInput` |
| `completed` / `failed` | `ParkOutcome.Done` / `Failed` |
| `tasks/update` inputs | the resume queue |
| `tasks/cancel` | park eviction on `notifications/cancelled` |

One real difference remains for P5c-2, and it is the interesting one: under MRTR the handler only
advances while a request is in flight, because the reader thread is waiting on the rendezvous.
A task advances in the BACKGROUND and is polled. Since the handler already runs on its own
virtual thread, that is a subtraction rather than an addition — the dispatcher simply stops
waiting. What it does require is that the park publish its state into itself rather than only
into the rendezvous queue, since for a task there is no one waiting to take from it.

### 10.3 What P5c-1 landed

Methods, statuses and the terminal partition; `clientSupportsTasks`, read per request because
this revision has no session to remember it in; `createTaskResult` and `taskResult`; and the
input parser, which unwraps the `{value: …}` envelope that is the one place the tasks shape
differs from MRTR's, while accepting a bare value too.

`taskResult` **enforces** its invariants instead of trusting the caller: a task carrying both a
result and an error is refused, as is a `completed` without a result, a `failed` without an
error, and an `input_required` that does not say what it needs. These are `require`s rather than
comments because each produces a task no client could read, and the failure would otherwise land
on the client rather than on us.

Fourteen cases. The capability probe's negative control turned out sharper than predicted: making
it always answer "supported" fails ONE test, not the two expected, because a request with no
`extensions` block never reaches the membership check at all. Two branches, two tests, and the
control showed which is which.


### 10.4 P5c-2 as built — a task is a park nobody is waiting on

§10.2 predicted the wiring would be a subtraction, and it was. `srv.asTask()` publishes one new
outcome, `Detached`; the dispatcher answers with a handle and stops waiting; the handler carries
on. Everything else — the virtual thread, the unguessable token, the TTL, the cancellation
path — is P3c's, unchanged.

**The one addition the prediction named in advance.** The rendezvous queue holds a single element
and, for a task, has no consumer. A detached handler that published through it would block
forever on its second publication. So a detached handler writes its state into the park, where
`tasks/get` reads it, and the queue stays the MRTR rendezvous alone. The terminal delivery uses
`offer` rather than `put` for the same reason: a finished handler must not block forever
delivering to nobody.

**A defect the tests found, and it is the interesting one.** `tasks/cancel` interrupts the
handler's thread. The interrupt surfaces inside the handler as an ordinary exception, the
handler's own `catch` turns it into a result, and the terminal publication then overwrote
`cancelled` with `completed` — telling the client the work it had just cancelled had finished.
Terminal status is now **write-once**, guarded on both sides, because the race runs both ways:
`tasks/cancel` already declined to overwrite a terminal status and the handler thread had to
learn the same manners. Worth stating plainly: the specification permits a cancelled task to
complete normally, so this is not a conformance failure — it is a truthfulness one, and those are
worse, because a client cannot detect it.

**Degrade, do not error.** `asTask()` returns `false` for a legacy client, for a server in
`Replay` mode, and for a client that never advertised the extension; the call then runs to
completion as an ordinary blocking one. Emitting `resultType: "task"` to a client that never said
it understands one is the protocol error — the spec calls an unrecognised `resultType` invalid —
so silence and a normal answer is the safe direction. A handler that genuinely cannot block asks
`clientSupportsTasks` and refuses on its own terms.

**Two small decisions the spec left open, and why they went the way they did.** An unknown
`taskId` answers `-32602`, the code this revision moved resource-not-found to, because the id is
a parameter that does not resolve rather than a missing endpoint. And a token that names a live
MRTR park rather than a task answers with *exactly the same message*: distinguishing them would
confirm to a caller who guessed a token that the token exists.

`tasks/update` against a task that is not `input_required` is refused rather than queued. Queued,
the answer would sit in the resume slot and be consumed by the NEXT question — pairing an answer
with a prompt nobody matched it to, which is the same class of silent wrongness as the
cancellation defect above.

**Evidence.** `mcpCommon` 601/601. Negative controls: making every client appear to support the
extension fails exactly the degradation case; deleting the MRTR-token guard fails exactly the
token-confusion case; and the write-once guard's control came for free in the natural order —
the cancellation test failed before it existed and passed after. Exposed to `.ssc` as
`srv.asTask()` and `srv.clientSupportsTasks()`, with the three false-answering cases spelled out
where an author will meet them.


## 11. Closing the gap §8.8 named — `.ssc` coverage for the whole surface

§8.8 recorded that the frame between a `.ssc` closure and an MCP intrinsic was argued rather than
measured. Three phases were then built on top of that argument, and by the time anyone counted,
`asTask`, `setMrtrMode` and `clientSupportsTasks` had **zero** coverage from `.ssc` — the Scala
API had six hundred cases and the binding a `.ssc` author actually uses had none.

`McpSscApiTest` runs real `.ssc` source through the real `Interpreter` and then drives the
resulting server with a real request. Nothing in it is a double: the tool handler is `.ssc`, the
callback is the interpreter's own, and the frame under test is the one that ships. The builder is
reachable because `mcpServer { … }` parks it in `Mcp.builderTL` and never clears it — the same
handle `serveMcp` picks up — and because that is load-bearing for the harness, the harness
asserts it rather than assuming it.

Seven cases: the MRTR signal crossing the frame, a parked `.ssc` handler resuming with a
`.ssc`-level counter reading **1** where replay would read 2, `asTask`, `clientSupportsTasks`
answered both ways from one program so the case cannot pass by always returning the same thing,
`setMrtrMode` compared across two modes, its refusal of an unknown mode name, and the
`requestState` round trip.

Two things the writing of it corrected:

- **`mrtrMode` and `parks` are `private[mcp]` and this test is not in that package.** That is the
  better outcome: the mode is now asserted through what a CLIENT can see — under `park` the
  result carries a `requestState` naming the parked handler, under `replay` the field is absent
  because nothing was kept — rather than by reading a field no client has.
- **The first version of that case was one-sided and failed**, because under replay with no author
  state there is no `requestState` at all. It is now a comparison: the same program under two
  modes, differing only in the `setMrtrMode` line.

Negative control: deleting `srv.asTask()` from the `.ssc` source fails exactly that case, which is
what makes these measurements of the binding rather than of the Scala API underneath it.

### 11.1 The paired-front check, and why it found nothing to fix

Before writing this, the two fronts were censused rather than assumed, since a feature present on
one path and missing on its twin is a recurring shape here. v1's `srv` exposes **40** members;
v2's native provider exposes **four** of them — `tool`, `resource`, `onConnected`,
`onDisconnected`. `elicit` and 32 others were already absent from v2 before any of this work.
So the new intrinsics are missing from v2 in exactly the way most of the surface already was:
a large, pre-existing, structural difference, not a pair broken here. Bringing v2's server
surface up to v1's is its own project and is not smuggled into this one.


## 12. `notifications/tasks` — the optional push, and a race a control uncovered

P5c-1 declared `Method.TasksNotification` and P5c-2 never wired it: a constant written and never
read, which passes every gate and is exactly the shape this project has a rule against. Wiring it
was the smaller of the two honest options, since the subscription machinery already existed and a
long-running task that can only be polled is the worse experience for precisely the case tasks
are for.

**Read, not guessed.** The filter is `{"notifications": {"taskIds": [...]}}` and the payload is
the full task, *"identical to what `tasks/get` would have returned at that moment"*. Both came
from the extension's specification page. Worth noting because the field is `taskIds` and the name
this would have been given by analogy with `resourceSubscriptions` is not that.

**Keyed by id, not by a flag.** A listen stream has no owner the server can check a task against,
so a blanket "send me my tasks" would put every task's state on every stream. Naming ids is what
the spec asks for and the only shape that is safe here.

**One renderer.** `tasks/get` and the push share `taskJson`, because the spec says they are the
same object and two renderers would have been two chances to drift — with the push being the copy
nobody looks at.

**Legacy streams are excluded explicitly.** A stdio client that never sent `subscriptions/listen`
has a `None` filter and otherwise receives every notification byte-identically. An extension's
notifications are the exception: that client opted into nothing.

### 12.1 The race, and why it was not a flaky test

The negative control for the legacy-stream rule was run twice. The first run failed **two** cases:
the intended one, and `tasks/cancel`. The second failed only the intended one. A test that fails
once and then passes is the shape of a flake, and treating it as one would have been wrong — the
same trap recorded earlier today, in the other direction.

`tasks/cancel` interrupted the handler's thread and *then* claimed the status:

```
th.interrupt()                                  // wakes the handler
if !isTerminal(status) then publish(Cancelled)  // …which may already have published
```

The interrupt surfaces in the handler as an ordinary exception, its own `catch` turns that into a
result, and its terminal publish can land in the window between the two lines. Write-once — added
in §10.4 for the mirror of this — then refuses the *cancel's* status, and the client is told
`completed` for work it cancelled. Write-once was necessary and not sufficient; the order matters
too. `cancelled` is now claimed **before** the interrupt, so the handler's terminal publish is the
one refused.

The fix is structural rather than probabilistic, which is the claim being made here: five green
runs do not prove a rare race gone, but a window that no longer exists does. A deterministic
complement pins the other side — cancelling an already-finished task must not rewrite it as
cancelled — because reordering cancel to claim the status first must not let it claim one that is
already taken.


## 13. Toward an honest `2025-06-18` on the legacy path

The P2d entry said the version string may rise to `2025-06-18` "only after P2b/P2c/P2d", and
named `context` on `completion/complete` as the outstanding piece. Those phases have landed, so
the follow-on was re-derived from the source rather than from that note — and the note was
incomplete. The revision's changelog carries **twelve** changes, not one.

The census, measured rather than assumed:

| 2025-06-18 change | Us |
|---|---|
| JSON-RPC batching REMOVED | compliant by never having had it — `JsonRpc.parse` reads one message |
| structured tool output, elicitation, resource links, `title`, protected resource metadata, `_meta` widening | already implemented |
| `context` on `CompletionRequest` | **was missing** — landed here |
| `MCP-Protocol-Version` header on HTTP requests | **was missing on our CLIENT** — landed here |
| RFC 8707 Resource Indicators, client-side | **still missing** — §13.2 |

Direction of error matters here and decides the sequencing: under-reporting a version is harmless
and over-reporting is not, so the string does not move until the last row does.

### 13.1 What landed

**`context` reaches a completion handler the way `isCancelled` does, not as a parameter.** A
completion handler is `String => List[String]` in the registration API and in the `.ssc` binding;
widening that arity would have rewritten every caller to serve the few that want the context.
`srv.completionContext` is read inside the handler instead, and it is cleared in a `finally` so it
cannot leak into the next one — asserted, since a thread-local that outlives its scope is the
failure this shape invites.

**The client states the version it actually speaks.** Before `connect()` that is the legacy
answer, which is the era the old client in fact spoke by sending `initialize` and nothing else;
after negotiating modern it says `2026-07-28`. Both are tested, because a constant would have
passed the first case and been wrong in the second.

That test stands up a real `HttpServer` and reads the header that ARRIVED. Grepping our own
request builder would have asserted that a line of code exists, which is a different claim: a
header is only observable from the other end. Negative control: deleting the line fails both
cases.

### 13.2 What is left, and why the version string has not moved

RFC 8707 Resource Indicators — **✓ landed 2026-08-13**, see §13.3. With it the census in §13 has
no missing row left, and the version string may rise; that is its own change and its own
verification.


### 13.3 RFC 8707 Resource Indicators

2025-06-18 makes these a **MUST** for clients, and the reason is specific rather than ceremonial:
without them an access token minted for one server can be replayed against another, so a
malicious server a client talks to can harvest a token meant for someone else. The `resource`
parameter binds the token to the server it was asked for.

Sent on **all four** request builders — authorization, code exchange, refresh, and client
credentials — and each carries the reason it is needed there rather than a cross-reference:
binding the code but not the token leaves the swap open at the last step; a refresh that omits it
widens the audience back out again; and a machine-to-machine token is as replayable as any other.

**Canonicalisation is not cosmetic.** Scheme and host lowercased, the scheme's default port
dropped, the fragment removed because RFC 8707 forbids it. Two decisions worth stating:

- **The path is KEPT.** Two MCP servers can share a host and differ only in path, and dropping it
  would defeat the parameter it is meant to carry. A test asserts `.../team-a/mcp` and
  `.../team-b/mcp` do not canonicalise to the same string.
- **A bare trailing `/` is dropped**, because `https://h/` and `https://h` name one resource while
  an authorization server comparing strings does not know that.

Input that does not parse is returned unchanged rather than rejected. This builds a request
parameter; failing a login over a URI the authorization server might well have accepted is the
worse error, and the parameter is checked by the AS, not by us.

**The `resource` argument is optional in the signature and that is not the same as optional in
the protocol.** It defaults to `None` so existing non-MCP callers keep compiling; for an MCP
client its absence is a defect in the CALLER, and the scaladoc says exactly that rather than
leaving the default to imply otherwise.

Five cases. The two that matter are driven through a recording endpoint rather than asserted on a
constructed string, so they measure the form that is SENT. Negative control: making
`resourceParam` yield nothing fails exactly those two and leaves the three canonicalisation cases
green — they test a pure function the control never touched.
